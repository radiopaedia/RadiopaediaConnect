1. Executive Summary

A targeted security review was conducted against the RadiopaediaConnect source code prior to deployment in a hospital environment. RadiopaediaConnect is an ASP.NET Core application that acts as a bridge between a hospital PACS system and the Radiopaedia.org platform, receiving DICOM images via a C-STORE SCP listener and uploading curated cases through the Radiopaedia API.

The review identified five confirmed vulnerabilities ranging from Critical to High severity. All five have been remediated within the same development cycle. The application is considered hardened and suitable for deployment following the changes described in this report.

2. Scope and Methodology

The review was conducted as a white-box source code analysis. All backend C# controllers, services, and data access components were examined, along with the React frontend. The focus was on vulnerability categories with direct exploitation potential given the application's deployment context: a hospital LAN with access to patient DICOM data and credentials for external services.

Component Technology Coverage
HTTP API ASP.NET Core 10 controllers Full review
DICOM SCP fo-dicom (FellowOak.Dicom) Full review
Authentication layer Custom BCrypt password, session cookie Full review
Data layer SQLite via Dapper Full review
Frontend React 19 / Vite Auth flows and API call patterns

Denial-of-service and resource exhaustion scenarios were excluded from scope as they are addressed through network-level controls outside the application. Third-party library version auditing was also excluded and is assumed to be handled by a separate dependency management process.

3. Findings

1
Unauthenticated DICOM C-MOVE Trigger Endpoint
Controllers/DebugController.cs — POST /api/debug/test-cmove
Critical Resolved

Description

A debug controller was present in the production codebase that exposed a POST /api/debug/test-cmove endpoint. The endpoint accepted a StudyUid, SeriesUid, and RemoteNode in the request body and directly invoked DicomScu.TriggerCMoveAsync, which issued a DICOM C-MOVE command to the specified PACS node. The controller carried no authentication attribute, and no global authorization policy was applied via app.MapControllers().

A default value of "SANTESRV1" was hardcoded as the fallback remote node, indicating the endpoint was written against a real hospital PACS rather than a test fixture.

Exploit Scenario

Any unauthenticated client with network access to the server could send the following request and cause the PACS to begin pushing the specified study to the application's SCP listener, from which the attacker could read or exfiltrate patient DICOM files:

Vulnerable code (removed)
[ApiController]
[Route("api/[controller]")]
public class DebugController : ControllerBase
{
    [HttpPost("test-cmove")]
    public async Task<IActionResult> TestCMove(
        [FromBody] TestMoveRequest request)
    {
        if (string.IsNullOrEmpty(request.RemoteNode))
            request.RemoteNode = "SANTESRV1";  // production node hardcoded

        var success = await _dicomScu.TriggerCMoveAsync(
            request.StudyUid,
            request.SeriesUid ?? "",
            request.RemoteNode);

        // No authentication. Accessible anonymously.
        return success ? Ok(...) : BadRequest(...);
    }
}

Remediation

The entire DebugController.cs file was deleted. Debug tooling of this nature should not be present in a production codebase. Any future diagnostic capability requiring DICOM operations must be gated behind the admin authentication mechanism.

2
Path Traversal via Unsanitized DICOM UIDs
Services/Dicom/DicomScpManager.cs — OnCStoreRequestAsync
High Resolved

Description

When a C-STORE request was received by the DICOM SCP, three DICOM tag values were read directly from the inbound dataset and passed without validation into Path.Combine to construct the storage file path:

  • StudyInstanceUID was used as a directory name
  • SeriesInstanceUID was used as a subdirectory name
  • SOPInstanceUID was used as the filename stem

DICOM UIDs are expected to contain only numeric digits and dots ([0-9.]), however the application performed no validation of this constraint. A malicious DICOM client could supply UID values containing path traversal sequences, causing files to be written outside the intended storage directory. The same vulnerability existed in a second SCP implementation in CStoreScp.cs.

Exploit Scenario

A DICOM client connecting to port 104 sends a C-STORE with crafted UID values. On Linux, this could write arbitrary files with attacker-controlled content to sensitive filesystem locations. The severity is compounded by Finding 3, which shows the SCP accepted connections from any client without AE title verification.

Before
var studyUid  = dataset.GetSingleValueOrDefault(
    DicomTag.StudyInstanceUID, "UNKNOWN");
var seriesUid = dataset.GetSingleValueOrDefault(
    DicomTag.SeriesInstanceUID, "UNKNOWN");
var sopUid    = dataset.GetSingleValueOrDefault(
    DicomTag.SOPInstanceUID, "UNKNOWN");

// No validation. UID used directly in path.
var folder = StaticRepository
    .GetSeriesStoragePath(studyUid, seriesUid);
var filePath = Path.Combine(
    folder, $"{sopUid}.dcm");
After
var studyUid  = dataset.GetSingleValueOrDefault(
    DicomTag.StudyInstanceUID, "");
var seriesUid = dataset.GetSingleValueOrDefault(
    DicomTag.SeriesInstanceUID, "");
var sopUid    = dataset.GetSingleValueOrDefault(
    DicomTag.SOPInstanceUID, "");

try {
    studyUid  = DicomRepository
        .SanitizeDicomUid(studyUid);
    seriesUid = DicomRepository
        .SanitizeDicomUid(seriesUid);
    sopUid    = DicomRepository
        .SanitizeDicomUid(sopUid);
} catch (ArgumentException ex) {
    Logger.LogWarning(
        "[SCP] Rejected C-STORE: {Msg}",
        ex.Message);
    return new DicomCStoreResponse(request,
        DicomStatus.InvalidAttributeValue);
}

Remediation

A SanitizeDicomUid static method was added to DicomRepository. It validates the UID against the regex pattern ^[0-9.]{1,64}$ and throws an ArgumentException on any non-conforming value. Both C-STORE handlers now call this for all three UID fields before any filesystem operation is attempted. A non-conforming UID results in a DICOM InvalidAttributeValue rejection response, which is the correct protocol-level response for this condition.

3
DICOM SCP Accepts Connections from Any AE Title
Services/Dicom/DicomScpManager.cs — OnReceiveAssociationRequestAsync
High Resolved

Description

The DICOM SCP's association request handler accepted every inbound connection unconditionally. The calling AE title was logged but never compared against any configured allowlist. A ConfiguredAeTitle static field existed on the service class but was never consulted during the association negotiation.

DICOM has no built-in cryptographic authentication. In practice, AE title filtering is the accepted access control mechanism for DICOM services on a clinical network. Without it, any device on the hospital LAN capable of sending DICOM traffic could push arbitrary data into the application.

Before
public Task OnReceiveAssociationRequestAsync(
    DicomAssociation association)
{
    // CallingAE is logged but never checked.
    Logger.LogInformation(
        "[SCP] Incoming from {AE}",
        association.CallingAE);

    foreach (var pc in
        association.PresentationContexts)
    {
        pc.AcceptTransferSyntaxes(...);
    }

    // All associations accepted.
    return SendAssociationAcceptAsync(
        association);
}
After
public Task OnReceiveAssociationRequestAsync(
    DicomAssociation association)
{
    var callingAe =
        association.CallingAE?.Trim() ?? "";

    if (AllowedCallingAeTitles.Count > 0
        && !AllowedCallingAeTitles
               .Contains(callingAe))
    {
        Logger.LogWarning(
            "[SCP] Rejected unknown AE '{AE}'",
            callingAe);
        return SendAssociationRejectAsync(
            DicomRejectResult.Permanent,
            DicomRejectSource.ServiceUser,
            DicomRejectReason
                .CallingAENotRecognized);
    }

    Logger.LogInformation(
        "[SCP] Accepted '{AE}'", callingAe);
    foreach (var pc in
        association.PresentationContexts)
    {
        pc.AcceptTransferSyntaxes(...);
    }
    return SendAssociationAcceptAsync(
        association);
}

Remediation

A static AllowedCallingAeTitles hash set was added to the service class. It is populated at SCP startup and on every SCP restart from the list of configured remote nodes stored in the application's settings database. Associations from AE titles not in the set are rejected using the DICOM CallingAENotRecognized reason code, which is the standard protocol response for this condition.

If no remote nodes have been configured (fresh installation), the allowlist is empty and all connections are accepted with a warning logged. This prevents the application from being inaccessible during initial setup. Once remote nodes are added and the SCP is restarted, the allowlist becomes active.

4
Protected Health Information Written to Application Logs
Services/RadiopaediaApiClient.cs — CreateCaseAsync
High Resolved

Description

Before dispatching a case creation request to the Radiopaedia API, the application serialized the full request payload to JSON and wrote it to the logger at Information level using an [API-DEBUG] prefix. The payload included patient-derived fields sourced from the DICOM dataset: clinical presentation text, patient age, and patient sex.

The application's DatabaseLoggerProvider captures all log entries at Information level or above for the RadiopaediaConnect.Services namespace and persists them verbatim to the AppLogs table in SQLite. These logs were then queryable via GET /api/logs. Any user with the admin password could retrieve the full clinical history of every case ever submitted through the application, without those users necessarily having authorised access to that patient data.

Before
var payload = new {
    presentation = draft.Presentation, // PHI
    age          = draft.Age,          // PHI
    gender       = draft.Gender,       // PHI
    system_id    = systemId,
    ...
};

var json = JsonSerializer.Serialize(payload);

// Full PHI payload written to persistent logs.
_logger.LogInformation(
    "[API-DEBUG] Sending Payload: {Json}",
    json);
After
var payload = new {
    presentation = draft.Presentation,
    age          = draft.Age,
    gender       = draft.Gender,
    system_id    = systemId,
    ...
};

var json = JsonSerializer.Serialize(payload);

// PHI fields replaced with static placeholders.
_logger.LogInformation(
    "[API] Case payload: system_id={Sid}," +
    " certainty={Cert}," +
    " age=***, gender=***, presentation=***",
    payload.system_id,
    payload.diagnostic_certainty_id);

Remediation

The [API-DEBUG] log statement was replaced with a structured log entry that records only the non-PHI operational fields (system_id and diagnostic_certainty_id). The three patient-derived fields are replaced with the static string ***. The full JSON payload is still serialised and transmitted to the Radiopaedia API unchanged; only the log output is restricted.

Separately, the GET /api/logs endpoint and all other admin-protected endpoints were migrated to session cookie authentication (see Finding 5), adding a second layer of access control over the log data.

5
Credentials Exposed via Settings API and Per-Request Password Transmission
Controllers/SettingsController.cs — GET /api/settings/local; all protected endpoints
High Resolved

Description

This finding covers two related issues that were remediated together.

5a. Secrets Returned Verbatim from Settings API

The GET /api/settings/local endpoint returned the Radiopaedia OAuth client secret and the SMTP account password as plaintext strings in the JSON response. An attacker who obtained a valid admin session could immediately retrieve both credentials. The Radiopaedia client secret in particular is a higher-privilege credential: it can be used to impersonate the application at the OAuth provider level and mint tokens for any linked user account.

A secondary issue was also identified: the POST /api/settings/password/recover endpoint accepted the Radiopaedia client secret as a recovery token with no authentication required. This effectively made the client secret a second, unauthenticated admin password.

Before (GET /api/settings/local)
return Ok(new {
    radiopaediaClientId     =
        settings.RadiopaediaClientId ?? "",
    radiopaediaClientSecret =
        settings.RadiopaediaClientSecret ?? "",
    smtpPassword =
        settings.SmtpPassword ?? "",
    // Secrets returned verbatim.
    ...
});
After (GET /api/settings/local)
private const string SecretMask = "********";

return Ok(new {
    radiopaediaClientId =
        settings.RadiopaediaClientId ?? "",
    radiopaediaClientSecret =
        string.IsNullOrEmpty(
            settings.RadiopaediaClientSecret)
        ? "" : SecretMask,
    smtpPassword =
        string.IsNullOrEmpty(
            settings.SmtpPassword)
        ? "" : SecretMask,
    ...
});
Before (PUT /api/settings/local) - mask not checked, value always overwritten
var entity = new LocalSettingsEntity {
    RadiopaediaClientSecret = request.RadiopaediaClientSecret,
    SmtpPassword            = request.SmtpPassword,
    ...
};
After (PUT /api/settings/local) - mask sentinel preserved, other values written through
var newSecret = request.RadiopaediaClientSecret == SecretMask
    ? previousSettings.RadiopaediaClientSecret
    : request.RadiopaediaClientSecret;

var newSmtpPassword = request.SmtpPassword == SecretMask
    ? previousSettings.SmtpPassword
    : request.SmtpPassword;

var entity = new LocalSettingsEntity {
    RadiopaediaClientSecret = newSecret,
    SmtpPassword            = newSmtpPassword,
    ...
};

5b. Admin Password Transmitted on Every API Request

All protected API endpoints previously required the caller to supply the raw admin password in an X-Admin-Password HTTP header on every request. The frontend stored the password in sessionStorage for this purpose. This design means the password traversed the network repeatedly and was accessible to any JavaScript running in the browser session.

In the Docker deployment, the application runs on HTTP rather than HTTPS before reaching a reverse proxy. Any network observer between the client and the container could capture the admin password from routine settings page activity.

Remediation

The authentication model was redesigned to use server-side sessions:

  • A new AdminSessionService maintains an in-memory map of cryptographically random 32-byte session tokens to expiry timestamps (8-hour lifetime). Tokens are generated using RandomNumberGenerator.GetBytes.
  • POST /api/settings/password/verify issues an HttpOnly, SameSite=Strict session cookie on a successful password check. The password itself is no longer stored or transmitted after this single call.
  • All protected endpoints now validate the session cookie rather than a password header. The validation is centralised in a shared AdminControllerBase class inherited by all three admin controllers.
  • POST /api/settings/logout invalidates the server-side token and clears the cookie. The password recovery flow also calls this endpoint to invalidate any active session before redirecting to the setup page.
  • The sessionStorage password cache was removed from the frontend entirely. The settings click handler in the main navigation checks GET /api/settings/session to determine whether an active session exists, showing the password modal only when needed.

The Secure flag on the session cookie is set based on Request.IsHttps at the time the cookie is issued. In production deployments where TLS is terminated at the reverse proxy, it is recommended to configure the application to trust the forwarded scheme header (X-Forwarded-Proto) so that the cookie receives the Secure attribute even when the backend connection is plain HTTP. The application already configures UseForwardedHeaders for this purpose.

5. Residual Risk and Recommendations

All identified vulnerabilities have been resolved. The following items are noted as operational recommendations rather than code-level findings.

TLS at the Reverse Proxy

The application container runs on HTTP internally. Ensuring that the reverse proxy enforces HTTPS for all client-facing traffic is the single most impactful infrastructure control remaining. Without TLS, the session cookie (while HttpOnly and SameSite=Strict) is transmitted in the clear.

DICOM Port Network Segmentation

Port 104 (DICOM C-STORE SCP) should be accessible only from known PACS hosts at the network level. AE title filtering, as implemented in this review, is a protocol-layer control; it does not prevent a malicious host from initiating a TCP connection. Firewall rules restricting port 104 to the IP addresses of authorised PACS systems provide defence in depth.

Admin Session Expiry

Admin sessions currently expire after eight hours. For a clinical environment, a shorter idle timeout (for example, two hours) may be appropriate depending on the operator's access policy. Session tokens are stored in-memory and are cleared on application restart.

Dependency Auditing

Third-party package versions were not reviewed as part of this engagement. Running dotnet list package --vulnerable and npm audit periodically is recommended to catch known CVEs in dependencies such as fo-dicom, BCrypt.Net, and the React ecosystem packages.

6. Conclusion

At the time of the initial review, RadiopaediaConnect contained a Critical vulnerability that allowed any unauthenticated network user to trigger patient data retrieval from the hospital PACS, alongside four High-severity issues covering file system traversal, uncontrolled DICOM access, PHI exposure in logs, and credential leakage through the settings API. All five were resolved within the same development cycle.

Following remediation, no Critical or High severity findings remain open. The changes address the primary attack surfaces introduced by the application's role as a DICOM-to-web bridge in a clinical environment. Subject to the operational recommendations in Section 5, the application is considered suitable for production deployment.
